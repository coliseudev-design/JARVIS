# ExecPlan F01 — fundação executável

## Resultado exigido

Web React/Vite, API Fastify e worker com PostgreSQL/pgvector + Redis sobem em desenvolvimento descartável. UI apresenta somente capabilities verdadeiras. Build, typecheck, testes e migration em banco vazio passam. OpenAPI contém rotas implementadas; contratos futuros ficam documentados à parte.

## Dependências

ADRs/contratos F00 integrados. A compatibilidade completa Hermes é gate de F05; problemas upstream não autorizam fingir chat funcional nem atrasam correções independentes de setup. Registrar qualquer avanço parcial de F01 enquanto o gate F00 estiver pendente.

## Ownership e sequência

1. A00 fixa ferramentas/manifests/lockfile; A01 revisa fronteiras e schema de status/erro/eventos.
2. A13 prepara Compose local (portas loopback, healthchecks, volumes nomeados, imagens fixadas), script de setup, CI e runbook.
3. A03 implementa `/health/live`, readiness com consultas reais, status e worker de verificação sem dados pessoais; única autoria de migrations.
4. A04 implementa shell PT-BR acessível com estados de conexão reais. Login/chat permanecem indisponíveis até fases próprias; não adicionar botões que fingem autenticar/conversar.
5. A14 testa falha de dependência, configuração inválida, migration limpa e repetida, worker/filas e consistência de contrato. A00 integra e executa setup limpo.

## Segurança desde a base

Credencial de migration é distinta de aplicação. DB da aplicação não usa superuser, BYPASSRLS ou ownership das tabelas. Configuração live incompleta falha fechada. Testes de desenvolvimento usam apenas credenciais locais descartáveis, nunca credenciais externas. Logs não incluem bodies, URLs de banco com senha ou tokens.

## Checks obrigatórios

- Instalação por lockfile, build e typecheck do workspace.
- Unit/contract tests com asserts sobre falhas e schemas reais.
- PostgreSQL real: extensão vector, migration em banco vazio e segunda execução segura; role da aplicação inspecionada.
- API: resposta funcional readiness com dependências; erro 503 quando dependência necessária falha.
- Worker: job sintético completa e confirma efeito esperado; mensagem da fila não define identidade de usuário.
- Web: build e carregamento via servidor, erro/desconexão visível sem dados fictícios.
- Repetição dos passos salvos de instalação/start; nenhum segredo em arquivos versionáveis.

## Critério de fechamento e continuidade

Registrar comandos/resultados/versões em `docs/evidence/F01-foundation.md`. Se Docker/pull/rede bloquear banco real, manter checks de integração como não executados e não declarar fundação validada. Após F01 passar, a próxima implementação é F02 (identidade); visual de F03 pode avançar com fixtures rotuladas conforme plano de ondas.
